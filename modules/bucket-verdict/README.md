# Bucket Verdict｜不同分桶的延遲資料，能判定服務目標嗎？

兩個結帳服務回報同一個時段的延遲。北區用 100 與 200 毫秒分桶，南區用 80、150 與 300 毫秒分桶。值班人員想知道，至少 80% 的請求是否在 120 毫秒內完成。工具會列出原始資料仍有可能達到的最好與最差結果。

## 重現 20 筆請求的判定

使用 Python 3.11 以上，僅需標準函式庫。

```sh
python verdict.py examples/checkout.csv --threshold-ms 120 --target .8 --quantile .9
python -m unittest -v
```

20 筆請求中至少需要 16 筆達標。分桶資料只足以確定達標數介於 **10 到 17 筆**，因此目標判定為 `indeterminate`。合併後的 P90 是第 18 筆，由分桶可知介於 **151 到 300 毫秒**。同一份輸入若把目標比例調至 50% 便可確定通過，調至 90% 則可確定失敗。跑 `--quantile 1` 時，最大值只知道至少是 201 毫秒。

## 輸入與適用條件

CSV 表頭為 `shard,le_ms,cumulative_count`。每個 shard 代表同一觀測期間內一組互不重疊的請求，列出小於或等於各上界的累積筆數，並用 `+Inf` 列提供總數。輸入可打亂列序。請先由原始紀錄或計數器增量取得同一期間的分桶；服務啟動以來的總計不能直接代表最近一小時。演算法假設延遲是非負**整數毫秒**。

- 對跨越目標時間的桶，桶內每筆都有可能達標，也有可能超時。加總完全落在門檻內的桶得到下界，加上跨界桶得到上界。
- 百分位數採最近秩次 `ceil(q × N)`。將每個桶的所有觀測移至允許的最小值，取該秩次得到下界；移至最大值則得到上界。開放尾桶可取任意大值，碰到它時以 `null` 表示無上界。整個過程依桶數工作，記憶體用量與請求筆數無關。
- 所有 shard 合計為零時回報 `no_data`。重複邊界、缺總數或累積筆數倒退會指出輸入錯誤。

測試建立 160 組小型直方圖，逐一列舉能產生相同分桶的原始延遲組合，獨立核對達標筆數與百分位數兩端。另涵蓋超過浮點精度的整數計數、空窗口與沒有上界的尾桶。[範例輸入](examples/checkout.csv) · [驗證程式](test_verdict.py)
